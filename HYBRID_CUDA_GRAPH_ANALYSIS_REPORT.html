별도 DVS worker process

DAVIS read부터 inference까지 하나의 spawned process 안에서 inline으로 처리한다. slice와 infer를 다시 나누지 않아 추가 IPC/scheduling boundary를 피한다.

CUDA Graph runner

입력 shape은 (1, 8, 2, 60, 80)으로 고정한다. warm-up 후 TDTracker forward와 decode를 capture하며 static input storage 주소를 유지한다.

Async pinned result ring

replay마다 blocking .cpu() 또는 synchronize를 하지 않는다. x/y/confidence 세 값만 pinned slot에 복사하고 완료된 최신 slot만 소비한다.

RITnet anchor fusion

NIR frame에서 얻은 ellipse axes/angle을 유지하고, confidence threshold를 통과한 DVS 결과로 center만 갱신한다. 기본 DVS 대상은 eye 0이다.

BinaRep 명세
OFF channel 0, ON channel 1 순서를 유지한다. 4개 time-bin은 각 bit로 OR되며 출력 값은 0~15이다. 15로 나누어 정규화하지 않는다. invalid x/y event는 제거한다. native C와 NumPy 구현은 event-by-event bit-exact 테스트를 통과했다.
결과 metadata
seq_id, DVS hardware timestamp, stack submit, CUDA ready, parent receive, publish monotonic timestamp와 submit→ready/parent/publish latency, fresh, source, state_age_ms를 포함한다.

Root cause analysis

병목 원인 우선순위

1

4090 두 장 → 한 장으로 GPU workload 집중 높은 확신

현재 RITnet eye0/eye1, TDTracker worker, UI/OpenGL이 모두 GPU 0을 사용한다. TDTracker 단독 1772Hz가 full runtime 765~874Hz로 하락하고 GPU 사용률이 90%인 결과와 정확히 부합한다.

2

CUDA completion batching과 async ring drop 높은 확신

GPU가 밀리면서 여러 CUDA event가 한 번에 완료된다. worker는 latest-only 결과만 parent에 전달하므로 실제 완료 infer가 800Hz여도 서로 다른 seq_id를 받는 parent fresh rate는 약 140Hz까지 낮아진다.

3

i9-13900K P/E-core scheduling과 affinity 부재 중간 확신

DVS worker와 eye process가 각각 여러 CPU core를 사용하며 1ms publisher/polling thread가 E-core로 이동할 수 있다. DVS slicing은 1000Hz를 유지하므로 CPU가 전체 throughput의 1차 병목은 아니지만 publish 지터에는 영향을 준다.

4

Python/ZMQ publisher 경로 중간 확신

매 1ms마다 datum 복사, metadata 구성, msgpack 직렬화, ZMQ send를 수행한다. full runtime에서 publish가 약 840~916Hz에 머문다.

아닌 것: TDTracker 모델 자체 또는 CUDA Graph capture가 느린 것은 아니다. 단독 replay가 1772Hz이므로 모델/graph만 교체하는 접근은 현재 병목을 해결하지 못한다.
